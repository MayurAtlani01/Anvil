## Project Overview

ANVIL is a Manifest V3 Chrome extension that turns any web page into a workspace for three kinds of study: **Reading**, **Interview preparation**, and **Exam revision**. Instead of copying text into a separate AI chat tab, ANVIL activates directly on the page you're already on — a selection toolbar, a collapsible feature rail, and a full side panel are all injected in place, so the context (the page, the selection, the mode you're in) never has to be re-explained.

The project is genuinely full-stack: a React 18 + TypeScript extension frontend (built with Vite and CRXJS) talks to a FastAPI + SQLAlchemy backend over a versioned REST API, with JWT authentication, a real relational schema (SQLite for local development, PostgreSQL in production), and a pluggable AI provider layer (Gemini or OpenAI-compatible). Every extension surface — popup, side panel, and content script — also works with **no backend running at all**, falling back to `chrome.storage.local` for persistence and to free public APIs (Free Dictionary, Datamuse, MyMemory) for word lookups and translation, so the extension is never left completely inert if the user hasn't configured a backend.

**Who it's for:** students and job-seekers who want a single tool that stays with them across reading, interview prep, and exam revision, instead of three unrelated apps.

**Why a browser extension:** the point of ANVIL is contextual assistance without leaving the page. A `sidePanel` and content-script pairing is the only way to get a persistent study surface that survives navigation and still sees the page's own text and selections.

<br>

## Why ANVIL

Most "AI study helper" tools follow the same interaction shape:

```
User → copies text → switches tab → opens AI chat → pastes text →
explains what they want → waits for an answer → switches back
```

ANVIL is built around collapsing that into:

```
User → selects text or opens the side panel → chooses a mode
     → gets a contextual toolbar or full panel, in place, on the page
```

Concretely, this shows up as:

- A **selection toolbar** (`SelectionToolbar.tsx`) that appears the moment text is selected on any page, with per-action buttons (Explain, Translate, Highlight, Note, Flashcard, Read).
- A **collapsible rail** per mode (`ReadingCollapsedRail`, `InterviewCollapsedRail`, `ExamCollapsedRail`) that stays docked on the page instead of requiring the side panel to be open.
- A **side panel** (`chrome.sidePanel`) as the full workspace, for anything that needs more room — flashcard review, interview sessions, PYQ browsing.

The three modes are a deliberate choice, not three unrelated features bolted together: reading, interview prep, and exam revision are the three things a student actually does inside a browser tab, and they share the same underlying subsystems (bookmarks, flashcards, spaced repetition, progress tracking) rather than duplicating them per mode.

## Key Highlights

**What this project demonstrates:**

`Manifest V3 extension architecture` · `chrome.sidePanel API` · `Shadow DOM content-script isolation` · `Service-worker message routing` · `Mixed-content / CORS bypass via background relay` · `FastAPI REST backend` · `JWT authentication` · `SQLAlchemy ORM with relational schema` · `Pluggable LLM provider abstraction (Gemini / OpenAI)` · `SuperMemo SM-2 spaced repetition (implemented twice — client and server)` · `Graceful multi-tier storage fallback` · `pytest backend test suite`

**A few things worth reading before the rest of the document:**

- **A backend that refuses to fake its own AI.** `AIService._ensure_configured()` in `backend/app/services/ai_service.py` raises a clean HTTP `503` if `AI_API_KEY` is unset — there is no hardcoded "sample" AI response on the server. The **extension**, however, layers its own client-side fallbacks (rule-based summarization, Free Dictionary/Datamuse lookups) on top of that `503`, so the two halves of the system have deliberately different "no backend" philosophies — see [AI Architecture](#ai-architecture).
- **The background service worker is a relay, not just a message bus.** Content scripts run on `http(s)://` origins and cannot call `http://127.0.0.1:8000` directly without hitting mixed-content and CORS restrictions, so `apiClient.ts` detects that it's running inside a content script and forwards the request to the background service worker instead, which is not subject to the same restrictions (`FORWARD_API_REQUEST` in `background/index.ts`).
- **SuperMemo SM-2 is implemented identically in two languages.** `frontend/src/services/storage/flashcardsService.ts` (TypeScript, for the offline path) and `backend/app/services/sm2_service.py` (Python, for the synced path) both compute repetition/interval/ease-factor with the same formula, so review scheduling behaves the same whether or not a backend is connected.
- **Three-tier storage fallback.** The `storage` adapter (`frontend/src/services/storage/storage.ts`) tries `chrome.storage.local` first, falls back to `window.localStorage`, and finally an in-memory `Map` — so the extension degrades rather than throwing if extension APIs are unavailable (e.g. running the panel as a plain web page during development).

## System Architecture

ANVIL is three independent codebases in one repository, connected by one optional HTTP boundary:

```
                     ┌────────────────────────────────────────┐
                     │        Chrome Browser (User)            │
                     │                                          │
                     │   ┌────────┐   ┌───────────┐  ┌───────┐ │
                     │   │ Popup  │   │Side Panel │  │Content│ │
                     │   │(action)│   │(sidePanel)│  │Script │ │
                     │   └───┬────┘   └─────┬─────┘  └───┬───┘ │
                     │       │              │            │     │
                     │       └──────┬───────┴─────┬──────┘     │
                     │              │              │            │
                     │       ┌──────▼──────────────▼─────┐      │
                     │       │  Background Service Worker │      │
                     │       │  (message router + relay)  │      │
                     │       └──────────────┬─────────────┘      │
                     └──────────────────────┼────────────────────┘
                                             │  REST over HTTP(S)
                                             │  (optional — extension
                                             │   works fully offline)
                                    ┌────────▼─────────┐
                                    │  FastAPI Backend  │
                                    │  (app.main:app)   │
                                    └────────┬──────────┘
                             ┌────────────────┼─────────────────┐
                             ▼                ▼                 ▼
                    ┌─────────────┐  ┌────────────────┐  ┌─────────────┐
                    │ SQLite /    │  │ Gemini / OpenAI │  │  (unrelated)│
                    │ PostgreSQL  │  │  (if AI_API_KEY │  │  Marketing  │
                    │             │  │   configured)   │  │  site on    │
                    └─────────────┘  └─────────────────┘  │  Vercel     │
                                                            └─────────────┘
```

Typical request flow for an AI feature:

```
User selects text → SelectionToolbar / Side Panel component
  → services/api/aiService.ts calls apiFetch()
  → apiFetch detects execution context:
      - content script (http/https page) → relay through background worker
      - popup / side panel (extension origin) → call backend directly
  → FastAPI router → services/ai_service.py → LLM provider (if configured)
  → JSON response → rendered in the calling component
  → on any failure (no backend, no AI key, network error) →
      client-side fallback path in aiService.ts runs instead
```

## Browser Extension Architecture

ANVIL is a **Manifest V3** extension (`frontend/manifest.config.ts`) with five cooperating surfaces:

| Component | File | Role |
|---|---|---|
| **Popup** | `src/popup/` | The toolbar-icon action — quick mode switching and a one-click launcher for the full side panel |
| **Side Panel** | `src/sidepanel/` | The primary workspace, using the native `chrome.sidePanel` API (`side_panel.default_path` in the manifest) |
| **Background Service Worker** | `src/background/index.ts` | A `type: "module"` service worker that owns context menus, side-panel open/close state, mode activation, and API request relaying |
| **Content Script** | `src/content/index.tsx` | Injected at `document_start` on every `http`/`https` page; mounts a Shadow DOM root so ANVIL's styles never leak into (or clash with) the host page |
| **Injected UI** | `src/content/*.tsx` | The floating selection toolbar, per-mode collapsed rails, and floating cards (audio player, flashcard creator, interview/exam cards), all rendered inside the Shadow root |

**Message passing.** All cross-surface communication uses a single discriminated-union message type, `AnvilMessage` (`src/messaging/types.ts`), covering everything from `TOOLBAR_ACTION` and `OPEN_SIDE_PANEL` to `HOVER_MEANING_QUERY` and `FORWARD_API_REQUEST`. `src/messaging/helpers.ts` wraps `chrome.runtime.sendMessage` / `chrome.tabs.sendMessage` with existence checks, so a message sent while the extension context is being torn down (a known Manifest V3 pain point) fails silently instead of throwing.

**The background worker as router.** `background/index.ts` is the busiest file in the extension. It:
- Registers three context-menu entries (`Explain with Anvil`, `Create Flashcard from Selection`, `Summarize Page in Anvil`) on install.
- Tracks whether the side panel is open via a long-lived `Port` connection (`anvil_sidepanel_port`), because Chrome's `sidePanel` API has no direct "is it open" query.
- Falls back to a `chrome.windows.create` popup window, and then to a plain tab, if `chrome.sidePanel.open()` fails — three fallback tiers for one feature.
- Pings the content script before injecting it again (`pingContentScript` / `injectContentScript`), avoiding duplicate script injection on pages that already have it.
- Relays outbound API calls for content scripts via `FORWARD_API_REQUEST`, since content scripts on `https://` pages cannot fetch `http://127.0.0.1:8000` directly (see [Challenges and Solutions](#challenges-and-solutions)).

## Frontend Architecture

Built with **React 18 + TypeScript + Vite**, bundled by `@crxjs/vite-plugin` so the same Vite dev server that gives HMR to a normal web app also produces a valid unpacked Chrome extension.

**State management — Zustand, one store per domain:**

`useAuthStore` · `useModeStore` · `useReadingStore` · `useInterviewStore` · `useExamStore` · `useFlashcardsStore` · `useBookmarksStore` · `useNotesStore` · `useProgressStore` · `useThemeStore` · `useToastStore`

Each store calls into a matching service in `src/services/`, rather than talking to `chrome.storage` or `fetch` directly — this is the seam that lets every feature run identically whether a backend is configured or not.

**Service layer (`src/services/`):**
- `services/api/*.ts` — TypeScript interfaces (`NotesService`, `FlashcardService`, `AIService`, etc.) that define the contract each feature depends on.
- `services/storage/*.ts` — concrete implementations backed by `chrome.storage.local`, each independently falling back to the backend via `apiFetch()` when a backend URL is configured, and merging local + remote results rather than picking one exclusively (see `flashcardsService.list()` for the clearest example of the merge strategy).
- `services/index.ts` — a single hub that wires interfaces to implementations, so a store never imports a concrete storage class directly.

**Structural layout:**
```
src/
├── app/            → root App shell
├── background/      → service worker
├── content/         → injected UI + Shadow DOM mount
├── modes/            → ReadingView, InterviewView, ExamView (side-panel screens)
├── components/       → shared UI primitives (Modal, Toast, QuestionCard, SidePanelShell, …)
├── messaging/        → typed cross-surface message contract
├── services/         → api interfaces + storage implementations
├── store/            → Zustand state
├── types/            → shared domain types (Note, Flashcard, Question, ProgressStats, …)
└── utils/            → class-name and color helpers
```

## Backend Architecture

Built with **FastAPI + SQLAlchemy**, using a conventional layered structure:

| Layer | Location | Responsibility |
|---|---|---|
| Routers | `app/routers/` | Endpoint definitions per domain (auth, notes, flashcards, exam, interview, progress, ai, bookmarks, annotations, health) |
| Schemas | `app/schemas/` | Pydantic request/response models, one file per domain |
| Services | `app/services/` | Business logic that isn't pure CRUD — `ai_service.py` (provider abstraction) and `sm2_service.py` (spaced-repetition math) |
| Dependencies | `app/dependencies/auth.py` | `get_current_user` (strict JWT) and `get_optional_user` (guest-mode-friendly) FastAPI dependencies |
| Core | `app/core/` | `config.py` (Pydantic settings) and `security.py` (bcrypt hashing, JWT issuing/decoding) |
| Models | `app/db/models.py` | SQLAlchemy ORM models — the source of truth for the schema |

The app is wired up in `app/main.py` behind a `lifespan` context manager that calls `init_db()` on startup — table creation is automatic (`Base.metadata.create_all`), with a caught exception and a warning log if the configured database isn't reachable yet, rather than a hard crash.

CORS is currently permissive (`allow_origin_regex=r".*"`), which matches an extension that can be loaded unpacked from an arbitrary `chrome-extension://` origin during development, but is worth tightening before treating this as a hardened public deployment.

## AI Architecture

ANVIL has AI integration at **two layers that intentionally behave differently when unconfigured**:

**1. Backend (`backend/app/services/ai_service.py`) — strict, no mock data.**
`AIService._ensure_configured()` checks `settings.AI_API_KEY` before every call and raises `HTTPException(503)` if it's empty. There is no hardcoded example response anywhere in this layer. Two providers are supported:
- **Gemini** — `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`
- **OpenAI-compatible** — `POST https://api.openai.com/v1/chat/completions`

Every AI endpoint (`summarize`, `explain`, `translate`, `generate_flashcards`, `evaluate_answer`) builds a prompt that asks the model to return **raw JSON only**, strips any ` ```json ` fencing the model adds anyway, and parses it into a typed Pydantic response model.

**2. Extension (`frontend/src/services/api/aiService.ts`) — resilient, always answers something.**
Each method tries the backend first via `apiFetch()`. If that fails (no backend running, backend returned `503`, network error), it does **not** propagate the failure — it falls back to:
- A **rule-based summarizer** (sentence splitting + first-N-sentence heuristic) for `summarize`.
- The **Free Dictionary API**, then **Datamuse** as a second fallback, for `defineWord` and as a component of `explain`.
- The **MyMemory Translation API** for `translate`.
- A single generated flashcard extracted from the input text, for `generateFlashcards`.
- A fixed, clearly-labeled feedback shape for `evaluateAnswer` if the backend is unreachable.

This split means the backend can be a strict, honest API (never inventing an AI response) while the extension itself is never left with a dead button — the trade-off being that the offline fallback quality is deliberately lower than a real LLM call.

## Authentication and Security

**Flow:**

```
Register (email + password)
  ↓
bcrypt hash (12 rounds) — POST /api/auth/register
  ↓
Login — POST /api/auth/login
  ↓
Verify hash, issue JWT (HS256, 24h expiry by default)
  ↓
Token stored in chrome.storage.local (anvil_auth_token)
  ↓
Subsequent requests: Authorization: Bearer <token>
  ↓
GET /api/auth/me — validated via get_current_user dependency
```

**Implemented:**
- Password hashing with `bcrypt` (12 salt rounds), never stored or logged in plaintext.
- JWT issuance and verification via `PyJWT`, with `sub`, `exp`, and `iat` claims.
- A strict dependency (`get_current_user`) for protected routes and an optional one (`get_optional_user`) for routes that should work in guest mode.
- Environment-variable configuration (`SECRET_KEY`, `DATABASE_URL`, `AI_API_KEY`) via `pydantic-settings`, with `.env` excluded from version control by `.gitignore`.
- No API keys or JWT secrets are ever sent to or stored in the extension's UI beyond the token itself.

**Explicitly not implemented (as of this inspection):** OAuth/social login, refresh tokens or token revocation, rate limiting, CSRF protection (mitigated somewhat by the Bearer-token model rather than cookies), and encryption at rest. `Settings.SECRET_KEY` also ships with an insecure development default (`"anvil-insecure-secret-key-for-development-only-change-in-prod"`) that must be overridden via `.env` before any real deployment. Treat these as [Future Scope](#future-scope), not current guarantees.

## Mode Architecture

```
ANVIL
│
├── Reading Mode      (default subView: "summary" / "notes")
│   ├── AI summarization + rule-based fallback
│   ├── Web Speech API text-to-speech
│   ├── Persistent highlights (Annotation model)
│   └── Page notes with tags
│
├── Interview Mode    (default subView: "rounds")
│   ├── Practice rounds (DSA / System Design / Technical / HR)
│   ├── Session runner + per-question answers
│   ├── AI-evaluated feedback (score, strengths, improvements)
│   └── Resume analysis
│
└── Exam Mode         (default subView: "pyqs")
    ├── Previous Year Questions, filterable by subject/topic
    ├── Formula bank with per-variable explanations
    ├── Revision notes
    └── Frequently-asked-topics ranking
```

**Mode selection and state.** `useModeStore` holds `{ mode, subView, tabContext }` and persists it via the `storage` adapter under `anvil_mode` / `anvil_active_mode`. Activating a mode from the popup or context menu sends an `ACTIVATE_MODE` message to the background worker, which:
1. Resolves the target tab ID.
2. Writes the new mode to `chrome.storage.local`.
3. Pings the content script and re-injects it if it isn't alive.
4. Broadcasts `SET_ACTIVE_MODE` / `SET_READING_HOVER_MODE` / `SET_READING_FOCUS` to **every** open `http(s)` tab (`broadcastModeToAllTabs`), so mode state stays consistent across tabs, not just the one that triggered the switch.

**Quick Access becomes mode-aware** because the content-script rail component rendered is chosen directly from `activeMode` state (`ReadingCollapsedRail` / `InterviewCollapsedRail` / `ExamCollapsedRail` in `content/index.tsx`) — there's no shared generic rail with feature flags, each mode has its own purpose-built rail component.

## Reading Mode — Technical Deep Dive

**Problem:** reading assistance needs to work with arbitrary, unstructured page text, without requiring the user to leave the page.

**Architecture:** `modes/reading/ReadingView.tsx` (side panel) and `content/ReadingContextualPopup.tsx` / `ReadingHoverOverlay.tsx` (in-page) both read from `useReadingStore`, which owns page text, summary state, and TTS playback state.

**Data flow:**
```
Content script extracts page text (EXTRACT_PAGE_CONTENT)
  → useReadingStore.generateSummary()
  → aiService.summarize() [backend or client-side fallback]
  → rendered as summary + bullet points + read-time estimate
```

**Implementation details:**
- Text-to-speech uses the browser's native `speechSynthesis` API directly — no external TTS service — with a speed control between 0.8x and 1.5x (`FloatingAudioPlayer.tsx`).
- Highlights are modeled as `Annotation` records with a `rangeInfo` (`startOffset`, `endOffset`, `textSnippet`) so they can be reapplied to the DOM on revisit, and a `color` from a fixed five-color set.
- Word lookups use `HoverMeaningPopover.tsx`, which calls `aiService.defineWord()` — Free Dictionary API first, Datamuse second.

**Limitations:** highlight re-application is text-snippet-based rather than using the more robust `Range`/`CSS.highlights` APIs, so highlights can silently fail to reapply if the underlying page content changes between visits — a reasonable trade-off for Manifest V3 content-script simplicity, but a real one.

## Interview Mode — Technical Deep Dive

**Problem:** interview prep needs both a structured question bank and a way to get feedback on free-text answers.

**Architecture:** `modes/interview/InterviewView.tsx` + `useInterviewStore` on the frontend; `routers/interview.py` + the `InterviewSession` / `Question` / `ResumeAnalysis` SQLAlchemy models on the backend.

**Data flow:**
```
GET /api/interview/rounds → pick a round
  → POST /api/interview/sessions → InterviewSession created
  → POST /api/interview/sessions/{id}/answer → per-question answer recorded
  → aiService.evaluateAnswer() → AI-scored AnswerFeedback (or the offline fallback score)
  → POST /api/interview/sessions/{id}/finish → overallFeedback computed
```

**Implementation details:**
- `AnswerFeedback` is a structured shape (`score`, `strengths[]`, `improvements[]`, `keyTakeaway`, optional `suggestedAnswerSnippet`) enforced by a Pydantic schema on the backend and a TypeScript interface on the frontend — the two are kept in sync by hand rather than via a shared schema generator.
- Resume analysis (`POST /api/interview/resume/analyze`) accepts an uploaded file and returns a `ResumeAnalysisResponse` (fit score, key strengths, skill gaps, recommended rounds, matching keywords) — the model backing the actual resume-parsing logic is defined by whichever `AI_PROVIDER` is configured; there is no separate resume-specific model.

**Limitations:** without an `AI_API_KEY` configured, both answer evaluation and resume analysis fall back to a fixed, clearly-generic response shape on the client — genuinely useful practice-flow UX, but not real feedback. This is a case where the "zero mock data" policy is enforced strictly on the server and loosened deliberately on the client (see [AI Architecture](#ai-architecture)).

## Exam Mode — Technical Deep Dive

**Problem:** exam revision needs fast lookups across a large, filterable set of questions and formulas rather than a conversational flow.

**Architecture:** `modes/exam/ExamView.tsx` + `useExamStore`; `routers/exam.py` + the `Question`, `Formula`, and `RevisionNote` models.

**Data flow:**
```
GET /api/exam/subjects, /api/exam/topics → populate filters
  → GET /api/exam/pyqs?subject=&topic=&difficulty= → filtered question list
  → GET /api/exam/formulas, /api/exam/revision-notes → supporting material
  → GET /api/exam/frequently-asked-topics → ranked topic list
```

**Implementation details:**
- `Formula` stores `variables` as a JSON array of `{ symbol, meaning }` pairs, so the formula bank can render a proper symbol legend rather than a single opaque explanation string.
- `frequencyRank` on `Question` (1–10) exists specifically to support a "most likely to be asked" ranking, surfaced via the dedicated `/frequently-asked-topics` endpoint rather than being computed client-side.

## Quick Access — Technical Deep Dive

**Problem:** a study assistant is only useful if it's fast to reach — a full side panel is sometimes too much friction for a one-off action.

**Architecture:** two complementary quick-access surfaces:
1. **`PopupShell.tsx`** — opened via the toolbar icon, shows the current mode, a one-tap mode switcher, and a bookmark toggle for the current page, all without opening the side panel.
2. **Per-mode collapsed rails** (`content/ReadingCollapsedRail.tsx`, `InterviewCollapsedRail.tsx`, `ExamCollapsedRail.tsx`) — docked directly on the page via the content script's Shadow DOM root, exposing the 3–5 most relevant actions for the active mode without requiring the panel to be open at all.

**Why this matters architecturally:** the popup and the rails don't share a single generic "quick actions" component with a mode prop — each rail is its own component with its own feature set, which keeps each mode's quick-access surface honest about what's actually useful in that mode, at the cost of some duplicated layout code across the three rail components.

## Spaced Repetition Engine (SM-2)

ANVIL implements the SuperMemo SM-2 algorithm **twice, deliberately** — once in TypeScript for the offline path, once in Python for the synced path — so review scheduling is identical regardless of which storage backend answered the request.

| Property | Client (`flashcardsService.ts`) | Server (`sm2_service.py`) |
|---|---|---|
| Inputs | `repetition`, `interval`, `easeFactor`, `rating (1–5)` | Same |
| Rating ≥ 3 | `interval = 1` (rep 0) → `6` (rep 1) → `round(interval × ease)` (rep ≥2) | Identical formula |
| Rating < 3 | Resets `repetition = 0`, `interval = 1` | Identical |
| Ease adjustment | `ease += 0.1 − (5−rating)(0.08 + (5−rating)×0.02)`, floored at `1.3` | Identical formula |
| Next review | `now + interval` days | Identical |

Because both implementations are hand-written rather than generated from one source, they're a place where a future refactor (shared package, or moving the calculation server-side only) is a reasonable simplification — see [Future Scope](#future-scope).

## Performance

- **Content-script injection timing:** the manifest specifies `run_at: "document_start"`, and the background worker actively checks whether the content script is already alive (`pingContentScript`) before re-injecting it, avoiding duplicate mounts on programmatic mode activation.
- **Shadow DOM isolation:** all injected UI renders inside a single Shadow root (`SHADOW_HOST_ID = 'anvil-learning-shadow-root'`), which avoids expensive style recalculation cascades from the host page's own CSS reaching ANVIL's UI (and vice versa).
- **Local-first data reads:** `flashcardsService.list()` and similar storage services read from `chrome.storage.local` immediately and only overlay backend data when it arrives, so the UI is never blocked on a network round-trip for data that's already cached locally.
- **AI request timeouts:** dictionary and translation lookups use an `AbortController` with a 3.5-second timeout, so a slow public API (Free Dictionary, Datamuse) can't stall the UI indefinitely.

## Data & Storage Architecture

ANVIL has **two independent persistence layers**, kept in sync by the extension's storage services rather than by the backend:

**1. Extension-local (`chrome.storage.local`)** — always available, works fully offline. Every domain (`notes`, `flashcards`, `bookmarks`, `annotations`, `interview` state, `exam` state, `progress`) has a dedicated `Storage*Service` class in `frontend/src/services/storage/` that reads/writes a single JSON blob per domain under a namespaced key (e.g. `anvil_flashcards_data`).

**2. Backend (SQLite locally / PostgreSQL in production)** — a normalized relational schema in `backend/app/db/models.py`:

| Table | Purpose |
|---|---|
| `users` | Account credentials, JWT subject |
| `bookmarks` | Cross-mode saved items, optionally user-scoped |
| `notes` | Page notes with color/tags |
| `annotations` | Highlights, with `range_info` for DOM reapplication |
| `flashcards` | SM-2 fields (`interval`, `repetition`, `ease_factor`, `next_review_date`) |
| `questions` | Shared table for both interview and exam questions (`mode` column differentiates) |
| `formulas` | Exam formula bank, `variables` stored as JSON |
| `revision_notes` | Exam revision content |
| `interview_rounds` | Practice-round catalog |
| `interview_sessions` | Session state, `questions`/`answers`/`overall_feedback` stored as JSON columns |
| `resume_analyses` | Resume-analysis results |
| `progress_entries` | Per-activity analytics events |

Most tables use a nullable `user_id` foreign key (`ondelete="CASCADE"` or `"SET NULL"` depending on the table), which is what allows the "guest mode" experience — data can be written and read without a logged-in user, and later attributed to an account if one is created.

**Merge strategy:** when a backend is configured, list-fetching services (e.g. `flashcardsService.list()`) query the backend, merge the result into the local cache keyed by ID (backend data wins on conflict), and persist the merged set back to `chrome.storage.local` — so switching backend URLs, or losing connectivity mid-session, doesn't lose local-only data.

## Challenges and Solutions

The repository has a short commit history (three commits), so there isn't a documented incident trail to draw a SEEMZ-style production postmortem from. The two problems below are ones the code itself was clearly built to solve — the evidence is the architecture, not a changelog entry.

### Content scripts can't call `localhost` directly

**Problem:** the content script runs in the security context of the page it's injected into. A content script on `https://example.com` trying to `fetch("http://127.0.0.1:8000/...")` hits both mixed-content blocking (HTTPS page → HTTP request) and CORS, neither of which a permissive backend CORS policy alone can fix, because mixed-content blocking happens in the browser before CORS is even evaluated.

**Investigation:** `apiClient.ts` explicitly checks for this condition — `isContentScript` tests for an `http:`/`https:` page origin combined with `chrome.runtime.sendMessage` being available — which only makes sense as a targeted fix for a problem that was actually hit.

**Solution:** requests from a content script are forwarded as a `FORWARD_API_REQUEST` message to the background service worker, which makes the actual `fetch()` call from the extension's own privileged context (not subject to the page's mixed-content/CORS restrictions) and relays the result back.

**Why this solution:** the alternative — requiring the backend to be HTTPS even for local development — would have made the "just works, no backend required" offline-first design much more fragile. Routing through the service worker keeps `http://127.0.0.1:8000` viable for local development without weakening the production CORS story.

### `chrome.sidePanel.open()` isn't guaranteed to succeed

**Problem:** `chrome.sidePanel` is a relatively new API, and `.open()` can reject depending on the calling context (e.g. no active tab, or being called outside a user gesture in some Chrome versions).

**Investigation:** `openSidePanelHelper` in `background/index.ts` wraps the call in a promise chain with two separate `.catch()` stages, escalating from `windowId`-based retry to a full fallback.

**Solution:** a three-tier fallback — try `sidePanel.open({ tabId })`, retry with `sidePanel.open({ windowId })`, and if both fail, open a same-sized `chrome.windows.create` popup window (or, as a last resort, a plain tab) pointed at the same `sidepanel/index.html`.

**Why this solution:** rather than surfacing an error to the user when the native panel API misbehaves, ANVIL degrades to a visually similar companion window so the feature never simply fails silently.

## Engineering Decisions

**Why Manifest V3 + `chrome.sidePanel` instead of a classic popup-only extension?** A popup closes the instant focus leaves it, which is unworkable for a multi-question interview session or a flashcard review queue. The side panel persists alongside the page.

**Why CRXJS over a hand-rolled Webpack/Rollup extension config?** It lets the manifest be defined in TypeScript (`manifest.config.ts`) and reuses the same Vite dev server and HMR pipeline as a normal web app, rather than maintaining a separate extension-specific build pipeline.

**Why Zustand over Redux/Context?** Ten independent, mostly-unrelated pieces of state (auth, mode, three mode-specific views, flashcards, bookmarks, notes, progress, theme) map naturally to ten small stores; Zustand's lack of boilerplate and provider nesting fits that better than a single global Redux store or a deep `Context` tree.

**Why Shadow DOM for the content script?** ANVIL's UI has to render correctly on top of arbitrary, unknown host-page CSS. A Shadow root gives style isolation in both directions without needing an `<iframe>` (which would complicate the selection-toolbar and hover-overlay interactions that need to read the host page's DOM).

**Why FastAPI over Express/Django?** Native async support (used throughout the AI router, since LLM calls are I/O-bound), automatic OpenAPI docs at `/docs`, and Pydantic-based validation that lines up naturally with a TypeScript-typed frontend.

**Why SQLAlchemy with both SQLite and PostgreSQL support?** SQLite requires zero setup for local development (`sqlite:///./anvil.db`, already present in the repo), while PostgreSQL is the production-grade default in `core/config.py` — the same ORM models work against either with no code changes, only a connection string.

**Why a strict 503 policy on the backend AI service, but fallbacks on the client?** A backend that silently returns fabricated "AI" text when no key is configured would be actively misleading. A client that does the same for a student trying to review flashcards mid-session would be actively unhelpful. Enforcing honesty at the API boundary while keeping the UI usable offline resolves that tension without compromising either.

**Why implement SM-2 twice instead of only on the server?** Flashcard review has to work in guest mode with no backend at all — deferring the calculation to a server that might not exist isn't an option, so the same algorithm is duplicated rather than shared.

## Learning Outcomes

Building ANVIL involved more than three feature screens wired to a database:

- Designing a Manifest V3 extension with five cooperating surfaces (popup, side panel, background worker, content script, injected UI) and a single typed message contract between them
- Solving a real mixed-content/CORS constraint specific to content scripts, via a background-worker relay rather than a backend workaround
- Building two independent persistence paths (offline-first `chrome.storage.local` and a synced SQL backend) that merge rather than conflict
- Implementing the same non-trivial algorithm (SuperMemo SM-2) twice, in two languages, and keeping them behaviorally identical
- Deciding — and enforcing at the code level — where "no mock data" should be strict (the backend AI service) versus where a resilient fallback is the right call (the client-facing AI experience)
- Structuring a FastAPI backend with a real dependency-injected auth system that supports both strict and optional authentication on the same routes
- Writing an automated backend test suite that specifically verifies negative-path behavior (the AI service's `503` when unconfigured), not just happy-path CRUD
